# 实验 1：检索评估（prometheus/prometheus，55 题）

**一句话**：在一个真实开源项目上测 Agent 的证据搜索，看它能不能找到包含答案的讨论、找不到时能不能老实说"证据不足"。顺带比较两个嵌入模型。

原始材料：[eval/README.md](../../eval/README.md)、[eval/labels.jsonl](../../eval/labels.jsonl)、[eval/annotation/](../../eval/annotation/)、代码 [agent/app/retrieval_eval.py](../../agent/app/retrieval_eval.py)、阈值 [agent/app/evidence.py](../../agent/app/evidence.py)。

---

## 1. 为什么要做

Agent 回答"为什么"的时候，要靠 `search_project_evidence` 去 PR 和 issue 的讨论里找依据。如果检索拿回来的是错的文档，后面的回答再好也没用。所以先单独测检索，把"找错了"和"答错了"两种失败分开。

## 2. 实验设计

### 语料

- 项目：`prometheus/prometheus`，时间窗口 2026-07-11 到 2026-10-08。
- 内容：PR 描述、PR 评论和评审、issue 正文和评论，**排除 bot**。
- 规模：123 个来源（40 个 PR、10 个 issue），切成 187 个块。
- 选它的原因：先抽了 10 个项目，看人类讨论和 bot 讨论的比例。`openai/openai-java` 的讨论大多是自动生成的，所以被排除。

> "来源"（source）是一条具体的文字：比如 `mr:19878:description` 是 PR #19878 的描述，`issue:19745:note:5736573241` 是 issue #19745 下的一条评论。"实体"（entity）是它所属的 PR 或 issue，比如 `mr:19878`。

### 检索流程（Agent 实际拿到什么）

1. 每个来源按段落切块，每块最多 1200 个字符。
2. 用嵌入模型把查询和每个块变成向量，计算**余弦相似度**（0 到 1，越高越像）。
3. 过滤：分数低于 0.30 的丢掉，bot 作者的丢掉。
4. **多样化**：同一个 PR 或 issue 最多保留 2 条，避免一个长讨论占满结果。
5. 返回前 8 条。
6. 如果第一名的分数低于阈值，标记 `insufficientEvidence`（证据不足）。

评估算的是**第 6 步之后 Agent 真正收到的东西**，不是向量库的原始排序。

### 问题集（55 题）

| 类型 | 数量 | 含义 | 例子 |
|---|---|---|---|
| 换说法（paraphrase） | 20 | 故意不用原文的词，考语义理解 | "重新加载配置后，服务发现刷新失败的指标为什么消失了？" |
| 关键词（lexical） | 15 | 用原文里的词，比如函数名 | "BucketFraction 收到空的 bucket 列表会怎样？" |
| 答不了，擦边（unanswerable-near） | 8 | 话题在语料里，答案不在 | 默认抓取间隔改动（语料里有讲抓取间隔的 PR，但不讲这个） |
| 答不了，无关（unanswerable） | 12 | 语料里完全没有 | — |

可答的 35 题，每题标出**所有**能回答它的来源。答不了的 20 题，标为空列表。

### 标注：做了两次

1. **第一轮**：Claude 读全文后标注，再逐条抽查（[eval/labels.review.md](https://github.com/lizheng-jp/dev-productivity-signals/blob/main/eval/labels.review.md)，在 main 分支）。
2. **第二轮**：OpenAI Codex **盲标**。只给它打乱顺序的问题、语料和书面规则（[eval/annotation/INSTRUCTIONS.md](../../eval/annotation/INSTRUCTIONS.md)），看不到第一轮的结果。

书面规则的核心：
- **相关**：来源自己的文字给出了答案，或答案的主要部分。
- **不相关**：只是提到话题、只是提问、只是说"我想做这个"。
- 答不了就给空列表，不许硬凑。
- 必须读全文，长 issue 的答案可能藏在很深的位置。

两轮的分歧按书面规则裁定，得到最终标签。

### 比较的模型

| 模型 | 说明 |
|---|---|
| `BAAI/bge-base-en-v1.5` | 默认模型，CPU 上运行 |
| `Qwen/Qwen3-Embedding-0.6B` | 截断到 768 维，CPU 上运行 |

Qwen3 的向量是用 `retrieval_eval reembed` **从同一批块**重新计算的。如果重新索引，会从 GitHub 拉到一份不同的样本，两个模型就不是在同一份语料上比较了。

## 3. 指标，逐个解释

只有可答的 35 题参与召回类指标的计算，答不了的 20 题单独统计。

### recall@k（前 k 名的召回率）

前 k 条结果里，包含了多少比例的相关来源。

> 例：某题有 4 个相关来源，前 3 名里有 2 个 → recall@3 = 2/4 = 0.5。

最终数字是 35 题的平均值。

### MRR（平均倒数排名）

第一个相关结果排在第几名，取倒数。第 1 名得 1，第 2 名得 0.5，第 3 名得 0.33，都没有就得 0。

> 它衡量"用户第一眼能不能看到对的"。recall 衡量"找全了没有"。

### entityRecall@3（实体级召回）

只要某个相关 PR 或 issue 的**任意一条**来源进了前 3，就算找到了这个实体。

> 它回答的是"找没找到对的 PR"，而不是"找没找到 PR 下面的每一条评论"。

### recallCeiling（召回上限）

因为每个实体最多返回 2 条，有些题**在设计上就不可能拿满分**。

> 例：第 2 题有 7 个相关来源，其中 6 个属于 PR #19165，1 个属于 #19873。#19165 最多只能返回 2 条，所以这题最多拿到 (2 + 1) / 7 = 0.43。

这个指标把"设计限制"和"排序错误"分开。

### Cohen's kappa（标注一致性）

两个标注者的一致程度，**扣除了碰巧一致的部分**。1 是完全一致，0 相当于随机。

> 为什么不直接看一致率？55 题 × 123 个来源 = 6765 对，绝大多数都是"不相关"。两个人都标"不相关"就能得到很高的一致率，但这不说明什么。kappa 修正了这一点。一般认为 0.8 以上就是很好的一致性。

### 证据不足的两个计数

- **答不了的题被正确标记**：20 题里有几题被标成证据不足。越多越好。
- **答得了的题被错误标记**：35 题里有几题被误判为证据不足。越少越好。

两者此消彼长：阈值调高，拦得住更多答不了的题，但也会误拦更多答得了的题。

## 4. 结果

### 标注一致性

| 指标 | 值 |
|---|---|
| kappa（6765 对） | 0.87 |
| 可答 / 不可答判断 | 55/55 一致（kappa 1.0） |
| 相关集合完全相同 | 40/55 |

15 处分歧**全部判 Codex 对**：
- 10 处：第一轮把只提问、只催促、只附和的评论标成了相关（比如"Can you also fix AppenderV2?"）。
- 5 处：Codex 在长文档深处找到了第一轮漏掉的答案。

### 检索结果

| 指标 | 随机 | bge-base | Qwen3-0.6B |
|---|---|---|---|
| recall@1 | 0.008 | 0.59 | **0.65** |
| recall@3 | 0.024 | **0.84** | 0.83 |
| recall@8 | 0.065 | 0.85 | **0.87** |
| MRR | 0.04 | 0.89 | **0.91** |
| MRR，关键词 / 换说法 | | 0.93 / 0.85 | **0.97 / 0.86** |
| entityRecall@3 | | 0.97 | 0.97 |
| 召回上限 | | 0.95 | 0.95 |
| 答不了被正确标记 | | **14/20** | 12/20 |
| 答得了被错误标记 | | 4/35 | **2/35** |
| 平均分：相关 / 其他 | | 0.78 / 0.66 | 0.70 / 0.49 |
| 嵌入 187 个块耗时 | | 约 1 分钟 | 约 44 分钟 |

"随机"是从 123 个来源里随机挑 8 个的期望值，用来说明检索确实在起作用。

## 5. 发现，以及为什么

**1. 标签噪声改变了结论。** 用第一轮标签时 recall@3 是 0.76，离上限 0.94 差很远。看起来像排序问题：短评论把有内容的评论挤出了前几名。裁定后 recall@3 变成 0.84。原来大部分差距是检索器**正确地**忽略了标签不该算进去的评论。
→ 第二位独立标注者带来的改变，比换任何模型都大。

**2. "找到对的 PR"已经解决了。** 两个模型的 entityRecall@3 都是 0.97。剩下的来源级差距很小，主要出在换说法的题上。

**3. 证据不足的阈值不能跨模型迁移。** 原来的 0.40 是为 Gemini 嵌入设定的。换成 bge 后，无关文字的平均分已经有 0.66，0.40 一题都拦不住（0/20）。现在每个模型单独设阈值：bge 0.73，Qwen3 0.59。
→ 余弦分数的绝对值在不同模型之间没有可比性。

**4. Qwen3 区分相关和不相关的能力更强，但没换。** 它的分差是 0.22（0.70 对 0.49），bge 只有 0.12。它的第一名也更准（recall@1 0.65 对 0.59）。但 recall@3 没有更好，而且在 CPU 上慢了约 40 倍。bge 保持为默认。
→ 几个百分点的差距在 35 题上属于噪声，速度差距是实打实的。

**5. 长文档必须读全文。** 标注时漏掉的答案，都出在长的 tracking issue 和提案里，答案藏在离开头很远的编号条目中。

**6. 来源级召回低估了检索效果。** 因为每个实体最多返回 2 条，召回上限只有 0.95。recallCeiling 和 entityRecall@3 把这个设计限制和真正的排序错误分开。

---

## 6. 局限

- **阈值在同一批题上调出来**：bge 0.73、Qwen3 0.59 都是在这 55 题上选的，所以"14/20 被正确标记"偏乐观。需要在新题或新项目上验证。
- **题目是读完文档再写的查找题**：不是 Agent 的主任务"解释指标为什么变化"。出题人先看过答案，关键词题天然偏容易。
- **样本小**：123 个来源、55 道题。模型之间几个百分点的差异在噪声范围内。
- **语料是采样**：后端只扫最近更新的前 100 条 PR 和 issue，所以只有 10 个 issue。
- **标注者都是语言模型**：Claude 和 Codex 互相核对，没有人类专家标注。
- **不可复现性**：重新索引会拉到不同的 GitHub 样本，标签里的来源 ID 可能就不存在了。`candidates.jsonl` 记录了当时标注所用的来源。

## 7. 面试可能被问到的问题

**Q：为什么要两个人标注？一个不够吗？**
一个人标注，错误是看不见的。第二个人盲标之后，kappa 告诉你标签有多可靠，分歧告诉你错在哪里。这次 15 处分歧暴露了一个系统性问题：第一轮把"只提问的评论"算成了相关。修正之后，结论从"排序有问题"变成了"排序基本没问题"。

**Q：kappa 0.87 算高吗？为什么不用一致率？**
0.8 以上一般算很好。不用一致率，是因为 6765 对里绝大多数是"不相关"，两个人随便标也能得到很高的一致率。kappa 扣除了碰巧一致的部分。

**Q：Qwen3 的大部分指标更好，为什么还用 bge？**
差距只有几个百分点，35 道题上这在噪声范围内，而且 recall@3 反而略低。但 Qwen3 在 CPU 上慢约 40 倍，这个差距是确定的。没有证据证明 Qwen3 更好，却有证据证明它更慢。

**Q：阈值是怎么定的？有什么问题？**
在这 55 题上选的：让答不了的题尽量被拦住，同时少误拦答得了的题。问题是在同一批数据上调参再评估，结果会偏乐观，需要留出集验证。还有一点：阈值不能跨模型迁移，因为不同模型的余弦分数分布不一样。

**Q：为什么既有 recall 又有 entityRecall？**
recall 看的是"每条相关评论都找到了没有"，entityRecall 看的是"找没找到对的 PR"。对 Agent 来说，找到对的 PR 往往就够了。而且因为每个 PR 最多返回 2 条，recall 有个低于 1 的上限，不能直接拿 recall 去判断排序好坏。

**Q：随机基线有什么用？**
证明检索确实有效，同时给出一个尺度。随机 recall@3 是 0.024，我们是 0.84，说明检索在起作用。

**Q：这个评估最大的问题是什么？**
它测的是查找题，不是主任务。而且题目是先读了文档再写的，偏容易。所以它能证明"能找到 PR"，但不能证明"能找到指标变化的原因"。
